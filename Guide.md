# Guide.md — Hermes: Installation → Models → Skills & Plugins

A step-by-step path from a bare machine to a fully configured Hermes setup with the requested skills and plugins.

---

## Step 1 — Install Hermes

```bash
# Fetch and review before running (don't pipe blind)
curl -fsSL https://hermes-agent.nousresearch.com/install.sh -o /tmp/hermes-install.sh
less /tmp/hermes-install.sh
bash /tmp/hermes-install.sh

# Reload shell
source ~/.bashrc      # or ~/.zshrc

# Verify
hermes doctor
```

Start it:

```bash
hermes
```

---

## Step 2 — Add / Choose a Model

```bash
hermes model
```

Pick your provider (Nous Portal, OpenRouter, OpenAI, or a custom endpoint) and model. Run `hermes doctor` again afterward to confirm the model connection is healthy.

---

## Step 3 — Mandatory Skills & Plugins

Install these by simply chatting with Hermes and asking it to set each one up — don't run install commands yourself. Each entry below includes what it does and exactly what to say to Hermes. **All three are marked mandatory for this setup** — get Hermes to install them before starting real project work.

> ⚠️ **Before asking Hermes to install anything below:** these are third-party, community-maintained tools from personal GitHub namespaces, not official Hermes/Nous Research releases. After each one, run `hermes doctor` to confirm nothing broke, and ask Hermes to summarize what the install script/plugin actually did before you trust it in a real project.

### 1. Ponytail
**Repo:** https://github.com/dietrichgebert/ponytail
**What it does:** An always-on "lazy senior dev" coding discipline skill. It pushes the agent toward the smallest correct diff instead of over-building — e.g., using a native `<input type="date">` instead of installing a date-picker library and writing a wrapper component. It ships as a native Hermes Agent plugin (bundled skills + slash commands), and benchmarks claim meaningfully less code and lower cost per task versus no skill, while still explicitly not cutting corners on security, data-loss handling, or accessibility.

**Say to Hermes:**
```
Install and enable the ponytail plugin from github.com/dietrichgebert/ponytail,
then confirm it's active and show me what /ponytail-help lists.
```

---

### 2. Agent-Reach
**Repo:** https://github.com/Panniantong/Agent-Reach
**What it does:** A "capability layer" that gives the agent reliable internet access — reading and searching Twitter/X, Reddit, YouTube, Bilibili, Xiaohongshu, GitHub, RSS, and more — by automatically selecting, installing, and routing between whichever backend (CLI, API, or MCP tool) currently works for each platform, and adapting when a platform changes its access method. Credentials/cookies are stored locally only.

**Say to Hermes:**
```
Set up Agent-Reach from github.com/Panniantong/Agent-Reach so I can search and
read content across platforms like Twitter, Reddit, and YouTube. Check first
whether it's confirmed compatible with Hermes, and tell me if anything about
the setup needs my review before it's enabled.
```

---

### 3. RTK
**Repo:** https://github.com/rtk-ai/rtk
**What it does:** A CLI wrapper/token-reduction toolkit for agent workflows. It sits in front of common CLI tools (git, gh, mypy, etc.), compacts their output, and rewrites verbose command results into a smaller, agent-friendly form — reducing the tokens your model burns per tool call. It has explicit, documented Hermes support.

**Say to Hermes:**
```
Install RTK from github.com/rtk-ai/rtk and initialize it for Hermes
(rtk init --agent hermes), then show me the savings dashboard (rtk gain)
so I can confirm it's working.
```

## Step 4 — Verify Everything

```bash
hermes doctor
```

Confirm no errors, then start a session and check that plugin/skill commands (e.g., `/ponytail-help`) respond as expected.

## Step 5 — Add PRD.md and HERMES-MANUAL.md, Start Development

Create a `<project_name>` directory, and inside it place:
- `prd.md` — your product/feature idea
- `HERMES-MANUAL.md` — the instruction set Hermes follows

Then open `hermes` inside that directory and tell it to read both files and begin. This kicks off the plan.md → human review → phase-by-phase implementation flow.

## Step 6 — One-Time Skills Setup (`HERMES-SKILL-BUILDER.md`)

Before starting project development, ensure all mandatory skills are present in the `skills/` directory — 14 generated by the builder plus 3 maintained directly (`context-compression`, `backend-development`, `frontend-development`), 17 in total:

1. In your workspace root (where `HERMES-SKILL-BUILDER.md` lives), open Hermes.
2. Send this single command:
   ```
   Read HERMES-SKILL-BUILDER.md and refer the manual.
   ```
3. Hermes will generate and verify the 14 builder-managed skills:
   - `plan-generation`
   - `task-generation`
   - `human-review-gate`
   - `github-setup`
   - `domain-clarification`
   - `phase-implementation`
   - `loop-engineering`
   - `multi-dev-merge`
   - `production-documentation`
   - `git-github-automation`
   - `deployment-verification`
   - `feature-tech-stack-change`
   - `microservices-adaptation`
   - `quality-checklist`

   Three additional skills are **not** generated by the builder and are maintained directly in `skills/` (back them up separately — re-running the builder will not recreate them):
   - `context-compression` — writes `SESSION-STATE.md` to compress context between phases.
   - `backend-development` — production-grade, technology-agnostic backend coding best practices, applied at Step 4.
   - `frontend-development` — production-grade, technology-agnostic frontend/UI coding best practices, applied at Step 4.
4. This is a one-time operation. Once `skills/` exists, these skills are available for all projects.

## Step 7 — The Human Playbook: Running Projects with Hermes

### 1. Prepare Your Project Folder
Inside your target project folder, ensure you have:
- `prd.md`: Describe your product or feature requirements. A rough description is completely fine—Hermes will ask if critical information is missing.
- `HERMES-MANUAL.md`: The autonomous execution manual for Hermes (keep unmodified in the project folder).
- `skills/`: The skills folder (or access to workspace skills).

### 2. Send the Single Kickoff Message
Start `hermes` in the project directory and send **only this message**:

```
Read prd.md and HERMES-MANUAL.md in this folder.
Follow HERMES-MANUAL.md exactly, start to finish, on your own, using the
mandatory skills it names at each step. Stop only at the human touchpoints
it defines.
```

### 3. Let Hermes Run
That is the only kickoff message you need to send. Hermes executes autonomously from Step 1 through Step 8 (or Step 10 for microservices), stopping **only** at the human touchpoints detailed below.

---

## Step 8 — Human Touchpoints (When Hermes Pauses and Waits for You)

Hermes will pause execution and request human input only at these specific gates:

| # | Step | When Hermes Stops | What You (the Human) Do |
|---|---|---|---|
| 1 | **Step 3** | Hermes completes `plan.md` and `task.md` | Review the plan and tasks. If satisfied, reply `approved`. If changes are needed, list them; Hermes will revise and re-present. |
| 2 | **Step 3.1** | GitHub repository setup & authentication | Provide your target GitHub repo name (`<owner>/<repo>`) and ensure your `GITHUB_TOKEN` is exported in your environment. |
| 3 | **Step 3.2** | Domain & operational parameters | Hermes presents a single, structured list of questions about business rules, retention periods, scaling limits, or edge cases. Answer them in your reply. |
| 4 | **Step 4** | Loop Engineering blocker (5 iterations reached) | If an automated build/test/fix loop fails 5 times on the same blocker, Hermes stops and reports the issue. Provide direction or decide how to proceed. |
| 5 | **Step 5** | Semantic merge conflict | If merging a branch creates a semantic conflict that cannot be resolved automatically, Hermes shows both conflicting versions. Decide which version wins. |
| 6 | **Step 9** | Tech-stack or architecture changes | When modifying existing core architecture, Hermes presents a diff of `plan.md` Sections 5–8. Review and re-approve just that diff. |
| 7 | **Step 10.A** | Microservices `SYSTEM-PLAN.md` | For multi-service projects, Hermes drafts `SYSTEM-PLAN.md`. Review and approve it before Hermes begins per-service implementations. |
| 8 | **Step 10.C** | Cross-service contract change | If an inter-service API contract needs modification, Hermes presents the diff in `SYSTEM-PLAN.md`. Approve before Hermes resumes code. |

## Step 9 — Mid-Project Control & Useful Commands

- **Requesting New Features or Stack Changes:**
  Speak to Hermes in plain English. For example:
  - *"Add a feature that lets users export their data as CSV"*
  - *"Switch the database from SQLite to PostgreSQL"*
  - *"Add Redis caching to the search endpoint"*
  Hermes will automatically route your request to **Step 9** (`feature-tech-stack-change`), update the relevant plan sections, and guide you through implementation.

- **Context Compression:**
  If the conversation becomes long, Hermes auto-compresses context after each phase. You can also trigger this manually at any time by sending:
  ```
  compress context
  ```
  or using `/compress`. Hermes writes `SESSION-STATE.md`, allowing a clean session reset with zero loss of progress.

- **Health Check:**
  If you ever suspect environment issues or broken plugins, run:
  ```bash
  hermes doctor
  ```
